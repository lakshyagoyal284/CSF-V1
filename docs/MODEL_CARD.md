# Model card — AgriTrust credit scorecard

| | |
|---|---|
| **Model** | XGBoost binary classifier (`binary:logistic`) |
| **Served artifact** | `artifacts/credit_model.pkl` |
| **Served by** | `ACS_MODEL_PATH` (default in `backend/config.py`) |
| **Output** | P(repaid on time) → 300–900 score, LOW/MEDIUM/HIGH tier, recommended limit |
| **Explainability** | TreeSHAP, grouped into credit concepts, converted to score points |
| **Version tag** | `acs-<engine_version>-<trained_at date>` |
| **Status** | Prototype. **Not approved for live credit decisions.** |

## 1. Intended use

Score a farmer or small-business applicant who has no bureau file, using declared
tangible assets (land, property, equipment, livestock, inventory) and
alternative cash-flow proxies (UPI turnover, utility payment discipline, bank
balances). The score is advisory: a bank officer verifies the evidence and makes
the decision. Borrowers never see the score.

Out of scope: consumer unsecured lending, salaried borrowers with bureau files,
automated straight-through approval without human verification, and any use as
the sole basis for a decline.

## 2. Training data

The served model is trained on `data/synthetic_portfolio.csv`, generated by
`ml/data_generator.py` with a latent creditworthiness process, a calibrated
repayment base rate, and label noise. 12,000 rows; 46% farmer / 54%
small-business; 77.5% on-time repayment.

**Every metric in this card describes a simulator, not a real loan book.** No
row corresponds to an actual borrower, and the generator's latent process is the
ceiling on what the model can learn (93% of that ceiling is captured on the
hold-out split).

### Experimental mixed-source model (not served)

`python scripts/train_combined.py` builds an optional model from four sources.
It is **not** a repayment model and must not be presented as one:

| Source | Rows | Target definition | Positive rate |
|---|---:|---|---:|
| `bank_dataset_2.csv` | 45,961 | `loan_status == Approved` (a **decision**, not repayment) | 71.8% |
| `mortgage_loan_dataset.csv` | 49,990 | `Loans Repaid >= 10` (history depth, not this loan's outcome) | 15.0% |
| `credit_ratings.csv` | 17,939 | issuer `defaulted` (issuer-level, no applicant features) | 97.7% |
| synthetic | 12,000 | on-time repayment | 77.5% |

The mortgage file records monetary values in **USD** while the bank and
synthetic files are effectively in INR; the mapping currently writes them into
the same numeric columns without an FX conversion. Ratios computed inside the
mortgage subset stay internally consistent, but absolute income/loan values are
not comparable across sources.

Because the labels are incompatible, the model learns to recognise the source
from missingness patterns. Measured on a 30k sample: overall ROC-AUC 0.890, but a
source-only baseline scores 0.844, within-bank AUC is **0.527**, and within
issuer ratings it is **0.500**. `region_tier` is the top SHAP driver only
because it is set for the 9.5% synthetic rows and missing for the rest. Treat the
combined metrics in `artifacts/training_metrics_combined.json` as an artifact of
dataset mixing.

## 3. Features

49 model inputs, frozen in `ml/config.py::FEATURE_COLUMNS`:

- 22 raw numeric declarations (age, dependents, years in operation, land,
  irrigation, soil, crop value, land/property/equipment/livestock/inventory
  values, shop area, UPI turnover, utility score/delays, bank balance, income
  proxy, debt, EMI, requested amount/tenure)
- 12 engineered ratios (collateral coverage, debt/asset, debt service, proposed
  debt service, post-facility LTV, liquidity, income/debt, net worth, asset
  productivity, financial discipline)
- 15 one-hot categorical levels (segment, region, shop ownership, crop)

Missing values are **not imputed** at training or serving time; XGBoost learns
the missing-value direction from the data. A missing declaration stays missing
rather than becoming zero.

**Protected attribute:** `age` is an input and is the third-largest driver in
the combined model (it is not in the top eight for the served synthetic model,
but it is still a model input). Many lending regimes regulate age and region.
Section 5 reports subgroup outcomes so this can be reviewed; a production model
should either justify age with a documented, tested policy or drop it and
retrain.

## 4. Performance (synthetic hold-out)

| Metric | Value |
|---|---|
| ROC-AUC | 0.87 |
| Gini | 0.74 |
| KS | 0.59 |
| PR-AUC | 0.95 |
| Brier | 0.11 |
| Train–test AUC gap | 0.04 |

Decile calibration is reported in `artifacts/training_metrics.json`. There is
**no isotonic/Platt calibration layer**; the deciles show the model is roughly
calibrated on this simulator, but PD must not be used for pricing without
hold-out calibration on real repayments.

Tier cut-offs: LOW ≥ 680 (PD ≤ 15%), MEDIUM 580–679 (PD ≤ 35%), HIGH < 580.
A data-quality overlay caps a thin file at MEDIUM even when the model likes it.
Recommended limits are the tighter of a collateral LTV cap and an income cap
(debt service ≤ 30% of income), haircut by tier.

## 5. Fairness monitoring

`ml/train.py` writes a `fairness` block to `training_metrics.json` for the
hold-out split, covering segment, region and age band with default rate, ROC-AUC
and pre-approval share. This is a monitoring report, not a fairness guarantee.
A production release needs:

- a documented acceptable disparity threshold per group,
- adverse-action reason monitoring (the `v_reason_code_frequency` view helps),
- validation on a real, consented loan book,
- challenger-model comparison and drift monitoring.

## 6. Limitations

- Synthetic data only (for the served model). No real repayment validation.
- No calibration layer, no reject inference, no bureau/AA data reconciliation.
- Declared values are trusted after banker verification; no Account Aggregator
  or UPI feed integration.
- Score clipping at 300/900 loses ranking at the extremes.
- No drift detection, no fairness sign-off, no production monitoring.
- The combined model's labels are proxies (see §2) and it must not be served as
  a credit model.
- Not validated against any regulatory requirement (RBI, ECOA/Reg B, GDPR/DPDP).

## 7. Monitoring and retraining

Before any live use: recalibrate on real outcomes, add population stability and
feature-drift alerts, monitor reason-code frequency and approval rates by group,
and retain the exact artifact + feature contract used for every decision (the
`credit_score_results` row already stores `model_version` and the SHAP payload).
Retrain with `python train_model.py`; the artifact carries its schema version,
feature list and metrics, and the API refuses a bundle whose contract drifts.
